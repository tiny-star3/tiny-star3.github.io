Xstar-Infer 推理引擎

多语言混合架构：C++/CUDA 手写算子与显存池 + Python 异步 Continuous Batching + vLLM 部署基线

跨层的方法论(每层都在用的)

  • 逐层对拍,不是端到端对拍:每层输入用 HF 的上一层输出,差异只反映”这一层”。跳过它=把多因素黑盒压成”一个 max diff”,无法定位。这不是省事与否,是 debug 的物理必然
  • 判据该严则严、该宽则宽:无计算层 torch.equal,镜像到位的计算层也能 bit-exact,带 bf16 噪声的层 allclose 宽容。用错的判据比没判据更糟
  • reference 随进度升级:阶段一 PyTorch 对 HF(抓架构 bug),阶段二 C++ 对你自己的 PyTorch(抓移植 bug)。每步只引入一个变量,bug 才被隔离
  • 引擎层不依赖 reference:xstar/layers/* 只 import torch,import transformers 只在 harness。阶段二换 reference 时引擎层不用改

对拍 Embedding 模块

  • “构造定结构、加载定数值”分离:__init__ 只建占位容器(torch.empty),真实权重靠 copy_ 单独灌。这是和 HF/vLLM 一致的加载模型——为阶段二”先搭图、后 mmap 权重”铺路。
  • 单一真相源:dtype/device/shape 都从 self.weight 这一个张量上读,不存副本。存副本会在 .to()/.bfloat16() 后和真权重分叉,assert 绿着却在撒谎。
  • 无浮点运算的层可以追求 bit-exact:torch.equal(不是 allclose)是合适的尺子——同源权重、同 token、纯查表,就该逐 bit 相等。判据该严则严。
  • 空壳的识别:torch.empty 占位如果忘灌权重,输出全是垃圾(一眼看出);随机初始化的空壳输出”形状对、数值平滑但全错”(难发现)。推理引擎宁可要”未初始化的垃圾”也不要”看着像的随机”

对拍 RMSNorm 模块

  • 精度镜像 reference,不是追求最优:升 float32 算中间方差→eps 加在 rsqrt 前→降回 bf16 再乘权重。每一步精度以 HF 为准,”比 reference 更准”在对拍里不是美德,是偏离
  • 带浮点运算的层也能 bit-exact:只要算子顺序、精度、dtype 完全镜像 HF,GPU 上确定性算子同输入同输出,RMSNorm 做到了 0 diff。这说明”allclose 宽容”不是带计算层的必然——算得对齐就能严
  • 在 float32 里看 bf16 的 diff:比差异时升 float32 再归约,避免 bf16 把 1e-4 的小差异 underflow 成 0,误判”完全相等”
  • eps 的位置是契约:sqrt(mean+eps) vs sqrt(mean)+eps 数学不等价,和 HF 同位置就行,不纠结哪个更对

对拍 RoPE 模块

  • hook 拿 HF 内部中间量:从外面挂 register_forward_hook,不改 HF 源码就能偷出 cos/sin/Q/K。”读源码理解机制,hook 验证实际数值”——两个都用
  • 配对方式是 RoPE 的命门:interleave vs split-half 都是合法 RoPE,但对同一权重产出不同结果。模型用哪种训练,推理就必须用哪种。以 HF rotate_half 为准,不是以你 CS336 旧实现为准
  • float32 缓存 + 用时降 bf16 的精度策略:cos/sin 存高精度(float32,三角函数更稳),用时 .to(x.dtype) 降到 bf16 和 HF 同路径。中间存更优、最终行为对齐——“和 reference 不一样”可以是”中间更优”,只要最终一致
  • 判据按 bf16 量级给宽:bf16 ~3 位有效数字,舍入误差 ~1e-3。cos/sin 用 atol=1e-2,旋转输出(浮点运算放大一点)也 1e-2。别用 float32 那套 1e-6 卡 bf16,纯噪声误报
  • 读 diff 量级判断对错:输入 cos 2e-3 → 输出旋转 5e-3(同量级、有因果)= 对;输入 2e-3 → 输出 1e-1(跳量级)= bug。量级的连贯性比一个 bool 的 allclose 信息量大得多
  • 直接调 HF 内部辅助函数要读它的形状契约:apply_rotary_pos_emb 内部 cos[position_ids] 决定了 cos 是 (位置,dim)、position_ids 才是 (batch,seq)——batch 结构在 position_ids 上,不在 cos 上。踩坑后立的纪律:形状不靠猜,print 出来看;报错类型(shape 错 vs CUDA assert)指向相反的修法

对拍 GroupedQueryAttention 模块

  1. 对拍方法论:逐段共模隔离 + diff 量级判读。 不只比最终输出,沿 forward 设断点逐段比 HF;单独测某段喂同一份上游输入(共模),diff 才只是该段自身误差。量级判读:2e-3→5e-3 同量级(正确)、→1e-1 跳量级(bug)。你这次 0.1592→0.0137(10x 下降)就是靠这条锁定因果掩码。读 diff 幅度,不读 diff 存在性。
  2. bf16 matmul 跨实现不比特一致是常态。 你 eager einsum vs HF SDPA,不同 CUDA kernel、不同累加顺序,bf16 下 1e-3~1e-2 差异不是 bug 是 GPU 浮点本质。直接带到 Phase 2:C++/CUDA kernel 和 PyTorch reference 也会有这层差异,容差要为它留——别指望 C++ port 比特等于 PyTorch。
  3. 容差带纪律(第 2 条的量化):容差夹在”噪声上界”和”bug 下界”之间,逐层测、逐层定,别统一 1e-2。 该严严(无计算层 torch.equal 比特严)、该宽宽(bf16 计算层 2e-2)。0.0137 卡在 1e-2 外 → 用 2e-2;若用 1e-1 会把 0.1592 那种真 bug 漏报。
  4. 对拍的固有盲区:只能验”和 HF 一致”,验不了”本身对不对”。 左 padding 不传 position_ids 也能”过”——两边同步犯错抵消。理解 HF 源码行为(model 层 cumsum-1 修正 position_ids)是对拍的补全,不是替代。 工具不抱怨≠正确(你 kwargs .attention_mask 报错前一直以为 mask 拿到了)。
  5. 多路径覆盖:多条代码分支要分别用不同输入触发,单测一种留盲区。 无 pad 走 else、左/右 pad 走 if——三种输入合起来才把 mask 子系统验全。
  6. hook 的边界与机制:只挂模块边界,中间结果(apply_rotary_pos_emb 后的 q_rot)hook 不到——用”已对齐组件复算”(HF q_proj 权重 + 你的 RoPE)绕过。 register_forward_hook 默认只给 posargs,HF 全用 kwargs 传参,要开 with_kwargs 才拿得到 attention_mask;kwargs 是 dict 用 ["key"]/.get() 取,不是 .attr。
  7. mask 设计:加性 finfo.min + causal 是 intrinsic(None 时自构,不靠 harness 喂)。 外部 mask 只是额外 padding 掩码叠在因果上。-inf vs finfo.min 在纯因果分支结果一样(对角线恒可见,不会全掩码行→不 NaN)——我之前催你改的”NaN bug”其实不存在,这是我臆造的,记一笔”别凭记忆下结论,读代码验证”。
  8. GQA repeat_kv 细节:RoPE 在 repeat 之前(省 7x 旋转);expand 只扩 size-1 维(插 None→扩 1→7→合并 2×7=14);头顺序 KV0×7、KV1×7 对齐 query 0-6→KV0、7-13→KV1。
  9. 左/右 padding 的场景语义:右 padding 是训练/HF generate 默认;左 padding 是批量 serving 偏好(末位真 token 恒在 -1,统一读 logits / append KV cache)。 两种都要支持。左 padding 真 token 物理位置≠逻辑位置,需 position_ids 修正

对拍 SwiGLU 模块

  1. 融合层的加载陷阱:concat 顺序必须和 chunk 拆分顺序对齐,反了是静默 bug(形状对、能跑、数值错)。 防呆:加载后 bit 对比前半 vs HF gate_proj。这条直接带到 C++ 阶段——你 C++ 里如果也融合 gate/up,同样的 concat 顺序坑会再出现。
  2. 共模输入纪律:ref 和你两侧喂同一份入口,diff 才只反映本层误差。 不喂共模,diff 混入上游,定位不清。
  3. 容差带实证:不同层噪声底不同(MLP 4e-3、attention 1.4e-2),容差逐层定。 这是”该宽则宽”的数据化——不是拍脑袋给 1e-2。

对拍 TransformerBlock 模块

  1. 归一化层(RMSNorm/LayerNorm)的 1/rms 因子把上游 bf16 噪声按比例放大,低量级激活(rms 小)放大更狠,但相对误差守恒——所以”绝对 diff 大”≠”实现错”,判 bug 看相对误差是否守恒。 这是本层最大收获,也是普适规律:Phase 1 C++ 对拍遇到同样放大不会误判成 port 错误。
  2. 逐段共模隔离:两侧必须各自独立从头算每一段,不能混用中间值。 你 rf_out = r1 + rf_m 曾混用你的 r1(污染段⑥)→ 改成 rf_r1 + rf_m。混用会让”段的对比”变成”子模块一致性的局部测试”,失去整块共模意义。
  3. 真 bug vs 放大的判别:真 bug 是”相对误差不守恒的跳量级”(如 4%→40%);放大是”相对误差守恒的量级变化”(4%→5%,绝对值因 1/rms 变大)。 这次 0.0137→0.4375 看着像跳量级,但相对误差守恒 → 放大,非 bug。
  4. block = 已验证积木的组合,没有新算法。 残差结构(pre-norm 双残差)、eps 从 reference config 读不写死、子模块 device/dtype 透传——都是把叶子层的纪律组合起来。组合层的风险不在”新逻辑”,而在”组装顺序”和”中间值不混用”。
  5. 容差带逐层定,组合层比叶子层宽。 子层:RMSNorm 0、attention 0.0137、mlp 0.004;block 因归一化放大到 0.1875,容差需 0.2。容差随”层数深度 + 归一化数量”递增,full model 会更宽——别指望整模型 1e-2。

对拍 Qwen2 模块

  1. 深层 transformer 是混沌系统:bf16 误差在 20+ 层会指数发散,深层 hidden_states / logits 不可能比特一致——这是数学性质,不是 bug。 判实现正确看”浅层 tight(layer0=单测值)+ 生成连贯”,不是”深层 allclose”。
  2. argmax 在平局处极脆:top-2 gap < 噪声幅度就会翻转,单点 top-1 不是好判据。 generate 一致性才是 reference 正确性的硬标准。
  3. 生成连贯 = reference 可用。 Phase 1 C++ port 验收也用这个:你的 C++ 引擎能生成连贯且和 PyTorch reference 高度重合的文本,就算 port 成功。
  4. 随机 token vs 真实文本:随机输入放大 bf16 发散(模型 OOD),真实文本更稳。对拍优先用真实文本,随机输入只验”不崩”。
  5. mask 形状必须严格对齐:2D mask 喂给 4D qk 会静默错(无 padding 时不爆,padding 时错)。 你这次抓到的 816→0.5 就是这个 latent bug——工具不抱怨≠正确。

oracle qwen2

1. 参考输出与判定分离(reference / judge 分家)。 不做”按层名一步到位”的函数,而是 reference 产期望、judge 判对错。职责单一:reference 只管算得对不对,judge 只管比得严不严。改判定逻辑不牵连参考产出,反之亦然。这是”造尺子”和”量东西”分开做。

2. 容差表一处定义、处处引用。 六层容差写成一个 TOLERANCES dict,judge 查表,调用方引用。改容差只动一个地方,且每层容差是独立标定的刻度(不是统一 1e-2)。面试讲”我给每层定了独立容差带”有据可查。

3. judge_mode 按层噪声特性分三类。 equal(无计算层比特一致)、allclose(bf16 噪声层带 atol)、amplified(归一化放大层 + 相对误差诊断)。把 Phase 0 你手工的”读 diff 量级、判放大还是 bug”固化成模式——不是统一一个 allclose 了事,而是该严则严、该宽则宽。

4. amplified 的 passed 和诊断解耦。 passed 走宽 allclose(绝对容差),relative_err 只塞进 Judgement 作诊断,不参与 pass/fail 判定。因为”守恒 vs 跳变”需要上下文(上游相对误差),自动化会误报,留给看 report 的人。判定和诊断是两件事,不搅进一个 allclose。

5. Judgement 是带诊断的结构,不是裸 bool。 passed + max_diff + relative_err + mode + layer + note。失败时 note 记录 shape/dtype 不匹配的具体值(cpp=(1,7,896) ref=(1,8,896)),一眼定位是哪维错了。FAIL 时不只说”错”,还说”差多少、哪不对、什么模式”。

6. 数据驱动显示,不判字符串。 report 用 j.relative_err is not None 决定显示 rel_err,用 j.note is not None 决定显示 note——字段是否填充决定显示,不是判断 j.mode == "amplified"。将来给别的模式加 relative_err,report 不用改。

7. 契约错误 vs 实现 bug 分两层暴露。 未知 layer(层名写错、model/lm 走 coherence)→ 抛 ValueError(调用方契约错误,立刻暴露);shape/dtype 不匹配(C++ 实现 bug)→ 判 FAIL + note(记录原因)。两种错误层次不同,不该用一种方式处理。mode is None 检查必须在 shape 检查之前,否则未知 layer 会被误报成 shape mismatch。

8. equal 模式对 C++ 侧提 dtype 契约。 embedding 是查表,equal 要求 C++ 侧原样返回 bf16、不转 f32——因为任何 dtype 转换都破坏比特可比性。judge 里 ref.dtype != cpp.dtype 直接判 FAIL + note 点破。这把”C++ 侧该怎么返回”写进了判定逻辑,不靠口头约定。

9. 数值比在 float32 上做,比特比在原始 dtype 上做。 max_diff 和 allclose 在 .float() 后算(bf16 精度不够,且 Phase 0 你就是这么做的);但 torch.equal 必须在原始 dtype 上——.float() 会把两个不同 bf16 映射到同一 f32,造成伪一致。同一对 tensor,数值判定和比特判定用两个版本,各司其职。

10. reference 用你的 PyTorch,不用 HF。 Phase 1 对拍是 C++ vs 你的 PyTorch(抓移植 bug),不是 C++ vs HF(会同时跨”架构差异 + 语言差异”两层噪声)。staged parity 的分界线就在这:HF 在 oracle 里只当权重来源,拷完释放,不留作判定基准。

层名 atol mode 依据
embedding None equal 纯查表,torch.equal 不看 atol
rmsnorm 1e-6 allclose f32 路径对齐
rope 1e-2 allclose f32 cache + downcast
attention 2e-2 allclose bf16 噪声 0.0137
mlp 5e-3 allclose bf16 底噪 0.0039
block 0.2 amplified RMSNorm 1/rms 放大,相对误差守恒

model/lm 不进表(走 coherence, 不经 judge)
