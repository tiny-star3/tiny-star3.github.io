M1 — 多请求 kernel + 前向

1. 多请求 attention 两种 kernel 设计,各有取舍

  • decode 用 per-warp-one-seq(8 warp 各一 seq,KV 直读 reg 不进 smem,32-lane 整 warp 归约)——为 splitKV 铺路(每个 warp 独立处理一个 seq,后续按 partition 拆开天然适配)。代价:与单请求 QUAD 归约不同加法顺序,decode 有 8-ulp 累积差。
  • prefill 用 3D-varlen grid + max 早退(FlashAttention varlen 形)——grid (ceil(max_q/Br), num_seqs, heads),blockIdx.y 直接索引 cu_seqlens 无二分,causal 段内化。与单请求同 QUAD 归约 → bit-exact。

2. 真 varlen(非 padding)的工程判断

  • paged_attention 无 mask,decode 每 seq 独立长度无法统一 padding;varlen 段隔离不做跨段 attention;工业 flashattn 原生支持。选 varlen 而非 padding 是和 paged/splitKV 路径一致的选择。

3. 路 B whole-batch write(vLLM reshape_and_cache 形)

  • 把 write 拆成 prepare_meta(只 layer 0 alloc+cursor+++block_table,无 scatter)+ 整批 slot_mapping[sum_q] + 一次 paged_write。K/V 不切片(head_split 是 head-outer,切 seq 是非连续轴)。对照 vLLM reshape_and_cache:整批一次 launch 而非 per-seq。

4. cursor 减不减 1 看读取时机,不看语义

  • decode 的 slot 用 cursor()-1(prepare_meta 已先跑,cursor 已 ++,旧值才是新 token 槽位);position 用 cursor()(forward 在 layer 循环前 build,prepare_meta 还没跑,旧值=新 token 绝对位置)。同是 decode,减不减 1 取决于「相对 prepare_meta 的读取时机」。

5. 三个 bug 的分层定位法(都是 probe 不臆断)

  • result shape 错(Q.shape().front()=num_heads 应 [1]=seq)→ add shape mismatch 直接暴露。
  • Q head-major vs kernel token-major → 改完后 prefill bit-exact 但 decode 还差,说明不是索引全错而是局部;再查发现蝶形归约漏 shfl_xor 8(32=2⁵ 要五步,只有四步)→ 补后 decode 从 1.3 掉到 0.25(ulp 层)。
  • 容差判据:先 probe max_diff=0.25 出现在哪(v≈-4.5 的 8-ulp 中值,不是大值 1-ulp),再定判据——rtol 帮不上中值,改 argmax match。

6. prefill bit-exact / decode 8-ulp 不对称 = 布局代价非 bug 的判据

  • 同布局(QUAD)→ 精确;不同布局(32-lane)→ ulp 差。这个不对称是「差异=布局不是隐藏 bug」的强证据。若有 indexing bug 会差 ~1.3 不会停 ulp 层。

7. 平局翻转=语义等价

  • real prompt step 13 seq2 翻(17 vs 16),生成「20世纪50年代」vs「1956年」语义等价。argmax 严格相等对 decode 8-ulp 不现实,平局翻转是 per-warp-one-seq 的已知代价,推理语义无害。

M2 — FastAPI

1. run_in_threadpool 包同步 GPU 调用是并发的异步前提

  • qwen2_forward_multi 是同步阻塞(GPU 调用),直接在 async def stream 里调会卡死整个 event loop,别的请求进不来 → 并发=0。run_in_threadpool 把它丢线程池,await 时 event loop 能处理别的请求。
  • why:GPU 调用不主动 yield event loop(Python GIL 释放≠loop 让出),必须靠线程池显式让出。这是 M3 中心调度器”一次 forward 喂 N 个请求”的异步根基 —— M3 不是每请求一个线程池调用,是调度器一个线程池调用喂 N 个。

2. lifespan 全局共享 vs 请求级局部的边界划在哪

  • 全局(lifespan 启动加载一次,只读):weights/cfg/rope/tokenizer/bm。局部(每 /generate 请求 new):PagedKVCache。边界判据:只读且全请求共用 → 全局;per-request 状态(各自 KV 在长)→ 局部。
  • bm 故意放全局不为 M2(单请求只用 2048 block),为 M3 多请求共享同一 block 池 —— 8 并发 × 2048 = 16384 blocks 这个容量也是为 M3 预留的。前瞻跟 M1 的”per-warp-one-seq 为 splitKV 铺路”同构。

3. 自回归闭环跨阶段变量形态分裂的分层定位(对标 M1 的 probe 分层法)

  • next_id 在 prefill 是 0-d(.argmax() 压维)、decode 是 [1](.argmax(-1) 保维),下面同一套代码(.numpy() 传 binding / decode([...]) 传 tokenizer)对两种形态行为不同 → 连环崩(0-d numpy 无 shape[0] → binding IndexError;1-d tensor 进 decode([tensor]) → TypeError)。
  • 关键:之前所有 parity 都是”喂固定 id 比 logits”非闭环,M2 是第一次自己写”argmax→喂回→再前向”闭环。prefill 那步形态对了不代表 decode 对 —— 要在每个阶段验变量形态,不能只验一层。统一成 1-d + tolist() 后四个用途(binding/decode/eos/reshape)形态统一不再分裂。

4. 跨语言边界的类型不能混用(C++ 枚举 ≠ torch device)

  • xstar_cpp.Device.CUDA 是 C++ 枚举,torch.to() 不认 → TypeError。要两个 device 变量:C++ 侧(load_qwen2_weights/BlockManager/PagedKVCache)用枚举,torch 侧(RoPE)用 device="cuda"。
  • 这跟 M1 的”减不减 1 看读取时机不看语义”一类 —— 都是”边界处的契约要精确,不能靠语义猜”。pybind/torch 是两套类型系统,枚举/device/numpy array 各对各的。

5. binding 契约要查实际调用,别看签名就断(我臆断被打脸)

  • binding 签名写 py::array_t<int64, c_style>,我断”cu_seqlens 传 python list 会崩”,你说”test 也这么写”,查 test L416 确实传 list 跑通 —— pybind 对 list of int 隐式转 int64 numpy(forcecast + c_style 生效)。
  • 教训:签名是必要非充分信息,真实契约要看实际调用能不能过。这条跟 M1 的”容差 probe 不臆断”同源 —— 别从一处静态信息推运行时行为。

6. 路径前瞻:用 multi 接口(num_seqs=1)跑单请求,M3 拉到 N kernel 零改

  • M2 看似单请求,但走 qwen2_forward_multi 而非 qwen2_forward_paged —— M1 的多请求 kernel(per-warp-one-seq decode + 3D-varlen prefill)就是为 M3 写的,M2 用它的 num_seqs=1 退化形态,M3 并发直接拉到 N,kernel 零改。
  • 取舍代价:M2 单请求付了”走 32-lane decode 带 8-ulp”的代价(见第 7 点),换 M3 接上零改。用未来阶段的接口跑当前阶段,跟 M1”per-warp-one-seq 为 splitKV 铺路”是同一类前瞻取舍。

7. “流畅输出 ≠ 正确”判据对 8-ulp 平局翻转失明(承接 M1 判据)

  • serve 走 multi 的 32-lane decode(8-ulp,M1 实证),HF 走不同实现(fp32 reduce),两者不 bit-exact,在某步平局 token 会翻(M1 real_prompt step13 实证:”20世纪50年代” vs “1956年”)。这种翻转生成的文本依然连贯流畅 —— 肉眼看文本判据对它完全失明。
  • M2 这条复发了 M1 的教训:数值正确性要靠 token id 对拍 + probe 平局(看翻的那个 token top2 差距),不能靠文本流畅度。M2 我省了这步(没做 parity,直接信流畅),证据强度弱于 M1 的 probe 实证 —— 这是已知判断弱项,债记着。判据本身没变,变的是 M2 没执行到底。

M3 — Continuous Batching

1. 调度器统一调用取代”每请求自调 forward”= M3 的结构地基

  • M2 是 stream() 里每请求自己 await run_in_threadpool(forward);M3 把 forward 调用权收归 _tick,一个 run_batch(decodes) 喂 N 个请求。请求只往 waiting submit,不自己驱动 forward —— 这是从”每请求一个 coroutine 跑 forward”到”一个调度器 coroutine 跑整批”的范式切换,continuous batching 的前提。
  • 承接 M2 第 6 点:M2 走 qwen2_forward_multi(num_seqs=1 退化)而非 qwen2_forward_paged,M1 的多请求 kernel 就是为 M3 写的。M3 把 num_seqs 从 1 拉到 N,kernel 零改 —— 跟 M1”per-warp-one-seq 为 splitKV 铺路”、M2”用未来接口跑当前阶段”是同一类前瞻取舍,M3 是那个”未来”落地。

2. Recompute 抢占的三段职责切分:reset 不碰 bm 是设计不是偷懒

  • PagedKVCache::reset() 只清自己的状态(cursor_=0 / block_table_.clear() / cuda_free(d_block_table_)),故意不碰 bm(头文件 docstring 写死 “Does NOT touch bm (no reference by design)”)。bm 的 block 释放是 scheduler 侧 bm.free(victim.kv.block_table()) 单独做。重 prefill 时 worker 喂 prompt_ids + generated_ids(完整,不是只 prompt)复现 KV。
  • why 切三段:PagedKVCache 不持有 bm 引用 → 析构/reset 不会误释放共享池里的 block(否则多请求共用一个 bm 会互相踩)。这是”职责边界要硬”——跟 M2 第 4 点”跨语言边界类型不能混用”同源:边界处的所有权契约要精确,reset 释放自己拥有的(d_block_table),不释放自己不拥有的(bm block)。

3. 抢占触发判据的保守性 + pool 大小的张力(两个 bench 口径别混)

  • 触发条件 num_free() < len(running)(vLLM v0.6.0 同款保守判据,不算 cursor 边界)。但这判据意味着只有池接近耗尽才抢 —— pool=16384(*8)时 24 并发 ×1000 token 才占 900 block,free 最低 536 >> 24,抢占永不触发;pool=150 时 8 并发 ~273 token 才触发。
  • 张力:pool 大 → 抢占不可达但 batch 能堆大(测吞吐口径);pool 小 → 能触发抢占但 prefill 长 prompt 易直接 OOM 抛 insufficient free blocks(不是优雅抢占)。标准 bench 用大 pool,抢占验证用小 pool,两者不能混 —— 这跟 M2 第 2 点”bm 全局为 M3 预留”的前瞻一脉相承,但 M3 暴露了”预留多大”本身就是个设计张力,不是越大越好。

4. binding 三处同改,漏一处 → 后台 task 静默崩 → 表象是 hang 不是报错

  • reset() 在 paged_kv_cache.h 声明、.cpp 实现都有,但 python_bindings.cpp 漏了 .def("reset", ...) → Python 侧 AttributeError: 'PagedKVCache' has no attribute 'reset'。这个 AttributeError 在 _tick 末尾 FINISHED 清理时抛,崩的是后台 _task 协程,没人接异常,表象是”请问”请求 hang 住(不是报错退出)。
  • 教训两条:(a) pybind 绑定是三文件契约(h/cpp/bindings),漏一个就崩,跟 M1”容差 probe 不臆断”、M2 第 5 点”binding 契约查实际调用别看签名”同源 —— 静态信息(声明在)不等于运行时可用(绑了没);(b) 后台 task 崩溃的表象是静默 hang 不是 crash —— 这是个新坑,排查时容易往”死锁/卡 GPU”想,实际是 task 已死。诊断要点:后台 task 一定要能让人看到它的异常(日志/或者 _loop 包 try 接住),否则就是隐形的。

5. bench 读出两个瓶颈:TTFT 固定开销平台 + 吞吐拐点 = memory-bound 显现

  • TTFT:短 prompt(1 token vs 21 token)中位数 0.123s vs 0.118s 几乎相同甚至反序,长 prompt(331 token)才跳到 0.817s → 短 prompt 被 ~120ms 固定开销平台主导(24 层 forward 的 kernel launch + Python→C++ 跨边界 + run_in_threadpool 调度 + 网络),prefill 计算量太小被淹没。
  • 吞吐:1→32 近线性 20×(8.9→181.5),32→128 边际骤降(+8.6%/+9.4%);TPOT 32→128 每翻倍近翻倍(176→325→594ms)。拐点 batch=32 = 权重访存摊薄红利吃完、KV 访存成主导的临界,memory-bound 教科书曲线实测落地。
  • 承接 M1 probe 分层法,但probe 的对象从”单 op 数值”变成”bench 曲线形状” —— 不是打印一层 tensor,是看曲线哪里不随长度变(固定开销)、哪里斜率变(拐点)。同样是”分层定位瓶颈”,M3 这层是宏观的。

6. bench harness 的 client 边界契约 —— 边界精确落到 client 侧

  • 四个踩坑:(a) httpx 0.28 Timeout(connect=,read=) 不给 default 直接报错,要么全四参要么给 default;(b) httpx.Limits(max_connections=200) 必设,默认连接池上限低,batch=128 测的是排队不是吞吐;(c) gather(*[stream_one(...) for _ in range(B)]) 要一次性构造 B 个 coroutine 并发,写成循环 await 就退化串行(测出来和 batch=1 一样);(d) SSE 的 data: {}\n\n 双换行,aiter_lines() 按单 \n 切出空行要跳,[DONE] 是结束信号不是 token 要排除。
  • 承接 M2 第 4 点”跨语言边界类型不能混用”——M2 的边界在 Python↔C++(枚举 vs torch device),M3 的边界在 Python↔HTTP/SSE(str vs bytes、连接池语义、并发原语)。同一类教训:每个边界都有自己的契约,不能靠语义猜,要查实际行为。

7. bit-exact 边界升级:从 M1”流畅≠正确”到 M3”bit-exact ≠ 路径等价”

  • 抢占 recompute 验证:victim 重 prefill 输出 vs 隔离单跑 400 token 逐个 bit-exact。但严格说,重 prefill 走 varlen 路径(一次性算 prompt+generated 的 KV),原 decode 走增量路径(逐 token 算),两条路在 bf16 下理论 8-ulp 差异(memory M1 实证)。bit-exact 是因为误差没翻转任何一步 argmax,不是两条数值路径等价。
  • 这是 M1 第 7 点”流畅输出对 8-ulp 平局翻转失明”的判据升级:M1 是”文本流畅 ≠ 数值对”,M3 是”bit-exact ≠ 路径等价”。两个方向都是强判据被弱证据满足时的警惕 —— M1 警惕”流畅骗你”,M3 警惕”bit-exact 骗你以为路径等价”。贪心确定路径下 bit-exact 成立,一旦上 sampling(temperature>0)或跨零临界 argmax,这个 bit-exact 就可能破 —— 这是 recompute 进真实 sampling 服务的命门。
  • 债(承接 M2 第 7 点的”没执行到底”):M3 的 bench 数(215.6 tok/s、”接近饱和”)没和理论算力上界对账。M1/M2 都强调 probe 对账防手滑,M3 这里”接近饱和”是看曲线形状(边际骤降)推断的,不是算这块 GPU 的 TFLOPS/带宽理论 tok/s 上界对比出来的。跟 M2 第 7 点”M2 没做 parity 直接信流畅”同构 —— 判据在,但这次没执行到底。已知弱项,债记着。
